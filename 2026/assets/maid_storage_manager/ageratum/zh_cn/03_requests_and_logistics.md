# 请求与物流

## 请求单

`request_list` 是核心的指令物品：你在上面写下想要什么，然后递给女仆。

它享受本附属复用配方的程度是独一档的——**它是唯一同时具备三种配方的物品**：

| 配方类型 | 效果 |
|:---|:---|
| `touhou_little_maid:altar` | 制作一张新的 |
| `maid_storage_manager:copy` | 复制一张已配置的清单 |
| `maid_storage_manager:list_clear` | 重置一张用过的清单 |

这个组合正是运行多名女仆时的设计流程：**认真写一张、为每名女仆复制一份、任务变更时重置副本。** 你几乎不需要制作第二张。

## 虚拟请求单

`virtual_request_list` 是与 `request_list` 不同的另一件物品，而且值得注意的是——**它是十五件物品中唯一没有任何配方的**，在 22 条配方里找不到它。

这意味着它不是你制作出来的东西，而是模组在运行过程中产生的。这与其名称相符：**它是作为运行时产物存在的请求，而不是你书写的文具。**

## 过滤器

`filter_list` 描述包含或排除什么。它有一条**复制配方**，因此一个精心构建的过滤器可以在多名女仆与多个工位之间复制。

过滤由代码中一套专门的「可过滤仓库」抽象支撑，**因此过滤作用于仓库访问本身，而不只作用于请求。**

## 物流指南

`logistics_guide` 是把一组已标记容器变成真实货物流动的那件物品。

它是模组中**唯一拥有两条不同魔法阵配方**的物品——普通版与另一个变体。同一物品有两条配方通常意味着两条成本不同的材料路径，**请在 JEI 或 EMI 中同时查看，取适合你当前阶段的那条。**

物流重试的上限相当宽裕：

| 选项 | 默认 |
|:---|:---|
| `behavior.max_logistics_tries` | **50** |

五十次远高于普通存放的三次，这反映出**一次物流运输有远多得多的暂时性受阻方式**——目标已满、路径被占、容器正被别人使用。

## 速度是逐活动可配的

`speed` 分节暴露了**六个独立倍率**而非一个全局速度，每个取值范围 `0.0`–`3.0`：

| 选项 | 默认 | 管什么 |
|:---|:---|:---|
| `speed.collect` | 0.5 | 收集物品 |
| `speed.place` | 0.5 | 放回物品 |
| `speed.view` | 0.3 | 查看容器 |
| `speed.view_change` | 0.5 | 在容器之间切换 |
| `speed.follow` | 0.5 | 跟随你 |
| `speed.crafting` | 0.5 | 合成 |

六个默认值全都远低于 `1.0`，这是刻意的节奏设计：**女仆应当看起来在干活，而不是把货物瞬移。** **`speed.view` 以 0.3 是最慢的一项**——查看是设计上的瓶颈。如果你觉得物流迟缓，这是首先该调高的数字，而代价是失去「女仆真的在读箱子」的观感。

## 容器访问被打了补丁，而这是有原因的

本附属六个 mixin 之一 `ContainerOpenersCounterPatch` 修补了原版的容器开启者计数。那是箱子盖开合、以及那些关心「容器当前是否正被使用」的方块背后的机制。**女仆以程序方式开启容器时必须被正确计数**，否则盖子会卡在打开状态、观察类装置会误触发。

它在游玩中不可见——而这类东西**只有在没做时才会以 bug 的形式显现**。
