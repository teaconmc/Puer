# AI 技能与通信

## 三份 AI 技能，投放进母模组

本附属向**车万女仆自己的数据命名空间**写入了三个文件，位于 `skills` 目录下。每个都是带 front matter 的 Markdown 文档——含**名称**、**描述**与一段正文说明。

它们不是给玩家看的文档，而是**给大模型驱动的女仆看的工具手册**：描述告诉模型何时使用该技能，正文告诉它调用哪个工具、怎么调。

| 技能 | 原文描述 | 它驱动的工具 |
|:---|:---|:---|
| `get_storage_manual` | *「回答任何关于物品与仓库的问题时使用。」* | `get_storage` |
| `find_storage_manual` | *「为用户查找并标记仓库中的物品。当用户询问某物的**位置**时使用此技能。」* | `find_mark_storage` |
| `fetch_item_manual` | *「当用户要求你为其查找或合成某物时使用。」* | `storage_fetch` |

正文写得很具体。`get_storage` 接受**一个可选的过滤模式**——不提供则返回全部物品。`storage_fetch` 会**生成一张请求单**，随后说明该任务将继续收集或合成清单上的一切，并在完成后交给玩家。

所以**自然语言路径与纸质路径是同一套机制**：**要求女仆取一样东西，字面上就是生成了一张请求单**，随后按你亲手写的那种方式执行。这是最干净的一种集成，也意味着你在 [03 请求与物流](03_requests_and_logistics) 学到的关于请求单的一切，同样描述了「你只是开口问」时会发生什么。

### 这依赖什么

这些技能是**母模组命名空间下的数据文件**。它们自身不做任何事——它们由车万女仆的对话式女仆功能消费。**若你的环境没有启用该功能，这三个文件就静静躺着，而本附属通过其物品照常工作。**

这一切在本附属自己的注册表、物品清单与配方里都看不到。**除非你去翻 `data/touhou_little_maid/skills/`，它是完全不可见的。**

## 可配置通信终端

`configurable_communicate_terminal` 是本附属用于另一种通信的物品：**女仆之间**。

代码中有一层专门的通信层——一个可通信接口、一个工具类、三个女仆行为（检查、准备、工作），以及一组菜单控件，含带「方法选择器」与「槽位选择器」的标记菜单，还有一个滚动文本显示。

「检查 → 准备 → 工作」这个形状描述的是一次**握手**：女仆先确认自己能参与、然后完成布置、再去做这件事。这正是**若干女仆能分工而不是重复劳动**的原因。

终端之所以叫「可配置」，体现在它的界面上：标记菜单让你挑选**方法**与**槽位**，因此**通信的内容是你设定的，而不是固定协议。**

## 一本你可能永远看不到的 Patchouli 手册

本附属随包 **40 个文件**的 Patchouli 手册内容，同样放在**车万女仆的命名空间**下而非自己的。

由此可得两点：

- **Patchouli 完全没有被声明为依赖**——既非必需也非可选。而且本附属**没有任何 Java 代码引用 Patchouli**；这些手册是纯数据。
- 因此该手册在**未装 Patchouli 时完全惰性**，其存在不产生任何代价。装了 Patchouli 之后，四十页游戏内文档会出现在母模组的手册里。

**这一点值得精确说明，正因为它极容易被误读成未声明依赖。它不是**：没有任何代码路径触及 Patchouli，所以不可能失败。它是可选内容，要么渲染、要么不渲染。

## 为什么放在母模组的命名空间下

技能与手册都被放在 `touhou_little_maid` 而不是 `maid_storage_manager` 下。这是刻意的：**两者都是母模组自身系统的扩展**——它的女仆技能注册表与它的手册——而这些系统的内容理应放在它们的命名空间下，母模组才找得到。

这与 [01 入门](01_getting_started) 中的魔法阵配方是同一种模式：**本附属一贯是接入母模组的既有结构，而不是另建一套平行体系。**
