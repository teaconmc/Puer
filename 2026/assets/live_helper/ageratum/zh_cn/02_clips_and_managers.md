# 分镜头与调度器

## 两类程序，两项职责

直播助手把机位控制拆成两个角色，每个角色由各自的 WebAssembly 程序驱动：

| 角色 | 原文术语 | 回答的问题 |
|:---|:---|:---|
| **技法（Technique）** | 技法 | *这个机位在哪里？朝哪个方向看？* |
| **调度器（Manager）** | 调度器 | *此刻哪一路上画面？镜头之间如何混合？* |

一个**分镜头（Clip）**就是一个机位：一段技法程序加上它所需的输入。一个**调度器**位于所有分镜头之上，逐帧决定转播实际呈现什么。

**这种分离就是整套设计。** 技法永远不知道自己是否在播出；调度器永远不计算机位坐标。你可以重写其中一方而完全不动另一方。

## 每一帧发生什么

1. **调度器**程序运行，返回一份帧渲染配置，描述哪些分镜头处于激活状态以及它们如何合并。
2. 对每个激活的分镜头，其**技法**程序运行并产出一个位置与一个朝向。
3. 各激活分镜头按该视点渲染。
4. 若调度器要求混合，结果按模组的 mix 着色器做**线性插值**合并。
5. 成品帧经 Spout 推出。

排查问题时这个顺序很重要：**看起来卡住的分镜头通常是技法的问题，而完全不出现的分镜头通常是调度器的问题。**

## 技法返回什么

技法会构建两者之一：

**一个固定视点** —— 三轴位置加上以**四元数**（四个分量）给出的朝向。用四元数而非偏航/俯仰，意味着任意两个朝向之间的平滑插值是有明确定义的，而这正是运镜所需要的。

**一个附着到实体上的机位** —— 机位跟随指定名称的实体，而不是持有坐标。

每个技法都会收到一个 `progress` 值，范围 `[0, 1)` 的浮点数，表示它在自己这段镜头中走到了何处。因此一次推轨运镜可以简单到「按 `progress` 在两点之间插值」。

## 调度器返回什么

调度器返回一份**帧渲染配置**，由两种操作构建：

**Single（单路）** —— 以给定进度激活恰好一个分镜头。这是硬切：一路画面上画面，其余不渲染。

**Mix（混合）** —— 取两份帧配置并按一个进度值混合。为 `0` 时只看到第一路，为 `1` 时只看到第二路，介于两者之间则线性插值。由于 Mix 接受的是帧配置而不是分镜头，**混合可以嵌套**：你可以混合一次混合，这正是三路转场的表达方式。

调度器必须从入口点**返回恰好一份配置**，而这份配置就是直播助手渲染的内容。

## 调度器知道什么

调度器获得了足以在不硬编码任何东西的前提下完成调度的信息：

| 输入 | 含义 |
|:---|:---|
| **分镜头数量** | 存在多少个分镜头，便于程序遍历全部 |
| 每个分镜头的**时长** | 以毫秒计，便于程序决定何时切换 |
| 每个分镜头的**名称** | 以文本给出，便于按名称而非下标选择镜头 |
| **已过时间** | 自调度器启动以来的毫秒数 |

分镜头以**从 0 开始的下标**寻址。名称是为了可读性而提供的，而读取一个名称需要两步调用，因为长度事先未知——见 [04 API 参考](04_api_reference)。

## 一个可用的范式

最简单而实用的调度器是「轮播 + 交叉淡化」：

1. 读取分镜头数量与每个分镜头的时长。
2. 由已过时间算出当前应上画面的分镜头，以及在其中的进度。
3. 若尚未接近该镜头末尾，返回带该分镜头与进度的 **Single**。
4. 若已进入交叉淡化窗口，为当前分镜头与下一个分镜头各构建一次 **Single**，然后返回 **Mix**，其进度值在窗口内从 0 爬到 1。

其余一切——硬切、定格在某一路、按已过时间做反应、带权重的轮转——都是这套骨架的变体。

## 这些东西存在哪里

分镜头、调度器、程序、仪表盘与输入声明全都由模组自己的存储层作为组件保存，并通过网页控制台编辑。程序有两种形态——**已编译的二进制**与**脚本**——因此你既可以上传构建好的模块，也可以把源码一并留在旁边。
