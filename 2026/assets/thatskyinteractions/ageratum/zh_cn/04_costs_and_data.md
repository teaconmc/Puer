# 解锁成本与数据结构

## 条件式好友树

服务端配置 `enableConditionalFriendship` 默认为 `false`。

- 关闭时，执行动作的路径不要求节点已经标记为解锁，玩家可以直接请求树上的动作。
- 开启时，节点必须按父子关系逐步解锁；未解锁节点不能直接执行，只有满足前置关系的节点可发起解锁。

无论配置值如何，只要实际发起并接受了“解锁”请求，服务端解锁代码都会检查请求者的物品余额，并扣除节点声明的成本。

::: warning
当前解锁实现的持久状态顺序有缺陷。条件模式开启时，代码先把节点写为已解锁，再检查余额。若邀请期间移走蜡烛，双人互动仍会先被接受，但不会发送节点解锁更新，服务端状态却可能已经改变；无余额的管理命令则会报告失败且不发送解锁更新，也可能留下已改变的服务端状态。条件模式关闭时，短路逻辑反而不会调用持久化解锁，只扣除成本并发送客户端控制包，逐节点状态可能在重新同步后丢失。
:::

## 两种货币

数据中的 `white_candle` 对应原版 `minecraft:candle`，`ascended_candle` 对应原版 `minecraft:red_candle`。余额只统计玩家物品栏中的对应物品，成本由发起解锁的一方支付。

整数形式的 `price` 默认代表白蜡烛；对象形式可以同时指定 `amount` 与 `currency`。

## 节点如何组成树

每个节点 JSON 可以声明：

- `parent`：父节点资源 ID。
- `branch`：相对父节点的 `left`、`middle` 或 `right` 分支；省略时使用默认分支。
- `behaviour`：好友、互动、牵手或锁等行为类型。
- `metadata`：例如互动 ID 与等级。
- `price`：整数白蜡烛成本，或包含货币类型的对象。

树构建器根据父节点和分支生成布局，并拒绝无法解析的互动或节点引用。修改成本或拓扑时，应同时检查两名玩家都能收到相同的数据同步结果。
