# 需求与优先级

## 一道菜就是一个布尔表达式

每条烹饪配方带一个 `requirements` 数组，其中每一项都是**八种需求类型**之一：

| 类型 | 含义 |
|:---|:---|
| **`CATEGORY_MIN`** | 某分类总量**至少**为 *n* |
| 分类下限（排他） | 严格**大于** *n* |
| 分类上限 | **至多**为 *n* |
| 分类上限（排他） | 严格**小于** *n* |
| 必须含有某食材 | 存在指定物品 |
| 必须含有某食材少于 | 该物品存在但少于 *n* 份 |
| 组合 AND | 全部子需求成立 |
| 组合 OR | 任一子需求成立 |

由于 AND 与 OR 本身也是需求类型，**需求是可嵌套的**。一道菜的条件是一棵**树**而非一张平表——你可以表达「至少 2 份肉，且（鱼或蛋），且不可食用少于 1」。

「包含/排他」成对存在在小数值下很关键：当某食材恰好贡献 0.5 时，`≥ 1.5` 与 `> 1.5` 是真的不同。

## 每种需求都有一个可绘制孪生类

八种类型各有一个对应的**可绘制（drawable）**类。这不只是代码整洁——它意味着**需求树会在 JEI 中被渲染出来**。

因此装了 JEI 就能**读到**一道菜的真实条件，而不必猜。**模组花了额外功夫让自己的匹配逻辑可读，这是它内部最友好玩家的一个决定。**

## 烹饪配方的几个字段

```json
{
  "type": "crockpot:crock_pot_cooking",
  "cookingtime": 200,
  "potlevel": 0,
  "priority": 10,
  "requirements": [ … ],
  "result": { "id": "crockpot:hot_chili" }
}
```

| 字段 | 含义 |
|:---|:---|
| `cookingtime` | 时长，单位刻 |
| **`potlevel`** | 所需最低锅等级 —— 见 [01 入门](01_getting_started) |
| **`priority`** | 决胜规则 |
| `requirements` | 条件树 |
| `result` | 菜品 |

## 🔑 优先级是没人猜得到的机制

同一组食材可能同时满足多道菜。发生时，**锅会做出优先级最高的那一道。**

这一个字段就解释了大部分令人困惑的行为：

- **多放一样食材会让结果变成毫不相关的另一道菜** —— 你跨进了某道更高优先级菜品的需求。
- **少放一样也会** —— 你掉出了高优先级菜，回落到了低优先级的那道。
- **一道理论上做得出的菜可能永远不出现**，只要总有一道更高优先级的菜同时被满足。

**游戏内对优先级毫无说明。** 如果你在追某道特定菜却总得到别的，说明你被压过了——去找你的配比还满足了什么。

## 瞄准某道特定菜

1. 在 JEI 里读那道菜的**需求树**（可绘制类使它可读）。
2. 记下它的**优先级**。
3. 检查你打算用的食材**还**在更高优先级上满足了什么。
4. 调整成「满足目标、同时**不满足**那个更高优先级的竞争者」——通常靠把某个分类压到它的**上限之下**，而不是靠多加。

最后这一点是实操诀窍：**上限与排他上限才是你的方向盘。多加东西很少能收窄结果，拿掉东西往往可以。**

## 给整合包作者

优先级是把你自己的菜整合进来而不破坏原有菜单的杠杆。**低**优先级的新菜填补空缺；**高**优先级的会遮蔽掉需求与它重叠的既有菜品。

需求是可嵌套的树，意味着你**很少需要新的需求类型**——把已有的八种组合起来即可。
