# 食材分类

## 十个分类

每种食材在十个分类中被打分：

| 分类 | ID |
|:---|:---|
| 肉 | `crockpot:meat` |
| 蔬菜 | `crockpot:veggie` |
| 水果 | `crockpot:fruit` |
| 鱼 | `crockpot:fish` |
| 蛋 | `crockpot:egg` |
| 乳制品 | `crockpot:dairy` |
| 甜味剂 | `crockpot:sweetener` |
| 冷冻 | `crockpot:frozen` |
| **怪物** | `crockpot:monster` |
| **不可食用** | `crockpot:inedible` |

最后两个才有意思。**怪物**标记来自敌对来源的食材，有几道菜要求它——这正是模组复现《饥荒》怪物肉菜品的方式。**不可食用**标记根本不是食物的东西，而菜品通常要求它**低于**某个阈值而非高于。

## 它们是数据包注册表，且每个只带一个颜色

分类位于 `data/crockpot/crockpot/food_category/`，每个分类一个 JSON，而每个文件**只含一个字段**：

```json
{ "color": 16755655 }
```

那是 `meat`。颜色用于显示（提示文本与 JEI），而它是一个分类**唯一**拥有的属性。

**由此得出两个重要后果：**

**分类是数据包注册表。** 数据包只要丢进一个带颜色的 JSON 就能新增一个分类，**无需给任何东西打补丁**。

**分类本身不携带规则。** 所有逻辑都在各道菜的需求里，而不在分类里。**一个分类只是一根带标签的打分轴。**

## 食材由 `food_values` 配方打分

分类归属**不是标签**，而是一种**配方类型**——`crockpot:food_values`——并且它是模组中数量最多的类型：横跨两个资源根共 **87 条**，多于真正的 60 条烹饪配方。

**所以模组用于描述「食材是什么」的数据比描述「有哪些菜」的更多。** 对一个「匹配」而非「罗列」的系统而言，这个比例是对的。

由于它是配方类型，**数据包可以重新归类任何物品**——为某个模组食材添加 `food_values`，它立刻就能参与烹饪锅，而无需改动本模组。

## 数值是小数

这个细节让整套系统像《饥荒》而不像 Minecraft 合成。辣椒炖菜要求：

| 需求 | 阈值 |
|:---|:---|
| 肉 | **≥ 1.5** |
| 蔬菜 | **≥ 1.5** |

不是「两份肉」，而是 **1.5 份肉**。单件物品贡献小数量，因此存在半值食材，两个半值加起来才是一整份。

实际影响是：**你无法用整件物品来推理这口锅。** 某个食材可能只算 0.5 份肉，于是三个能过 1.5 的线、两个不能。

## 在游戏里查看数值

模组专门为此提供了一个 JEI 分页——**Food Values** 页，显示哪些物品对应哪个分类。**如果你装了 JEI，那一页才是权威参考**，本页只是它背后的模型。

## 给整合包作者

| 想做的事 | 做法 |
|:---|:---|
| 新增一个分类 | 往 `crockpot/food_category` 丢一个带 `color` 的 JSON |
| 让某个模组物品可下锅 | 为它添加一条 `crockpot:food_values` 配方 |
| 重新平衡某食材 | 覆盖它现有的 `food_values` 配方 |
| 新增一道菜 | 添加一条 `crockpot:crock_pot_cooking` 配方 —— 见 [03](03_requirements_and_priority) |

**四项全部是数据包操作。这套系统就是为扩展而建的。**
