# 范围、本地化与网络

本页存在的理由是：自带语言文件远比模组本身庞大。如果你按翻译字符串 —— 或按一份旧 wiki、或按资源包导出 —— 来判断本构建，你会以为它有实际内容约三倍的东西。

## 精简构建

模组 id 是 `bsf3lite`。其语言文件带有 **176** 个物品名称键，但只有 **61** 个物品被注册。余下 **116** 个键指向本构建并不包含的内容：

| 类别 | 无对应注册物品的 lang 键 |
|:---|:---|
| 逐类型储存罐 | **64** —— 每种雪球各有一个 `*_snowball_tank` 与一个 `large_*_snowball_tank` |
| 追踪雪球 | 6 —— 轻型/重型/爆炸型，分别针对怪物与玩家 |
| 重力与斥力雪球 | 4 —— 各有针对怪物与针对弹射物的变体 |
| 异种雪球 | 8 —— 金、玻璃、黑洞、子空间、推进、末影、脉冲、幽灵 |
| 傀儡核心 | 9 —— 推进、迅捷、再生、暴击、斥力场、三种传送、运动预测 |
| 傀儡核心处理 | 2 —— 核心拆除器、空白核心 |
| 队伍连接器 | 16 —— 每种染料颜色一个 |
| 小游戏物品 | 5 —— 计分装置、可疑 U 盘、目标定位器、追踪核心、矢量反转锚 |
| 盆的状态 | 2 —— 盛雪的盆、盛细雪的盆 |

同样的落差出现在其他注册表里。语言文件命名了四个未注册的方块（自动售货机、区域控制器、区域控制器终端、区域玩家检查器）、五个场发生器实体（其中只有细雪扩散器存在）、一个追踪雪球实体，以及第三个叫 **Wallhack** 的状态效果。在整个 Java 源码中搜索 `wallhack`、`vending_machine`、`region_controller`、`scoring_device`、`target_locator` 与 `tracking_core`，返回**零**次命中 —— 它们是纯文本遗留，而非被禁用的功能。

最显眼的后果是整个**小游戏层**：语言文件包含一整套经济与反作弊词汇 —— 雪晶货币、等级要求、购买与回收提示、区域进入检查、「你已被踢出区域」通知、队伍加入与离开广播。这些在这里全都没有实现。只有一个幸存者：`region_tool` **确实**已注册，因此「区域」概念留下了一件没有方块可指的工具。

::: warning
不要围绕计分、队伍连接或区域系统规划服务器。它在本构建中完全缺席，只剩文本。同理，不要向玩家承诺追踪、重力、黑洞或子空间雪球 —— 本该供养它们的那 9 枚核心同样未注册，而**已**注册的两枚核心（`repulsion_core`、`gravity_core`）目前没有任何消耗方。
:::

## 本地化细节

随包发布四份语言文件：`en_us.json` 有 **511** 个键，`zh_cn.json`、`zh_tw.json`、`zh_hk.json` 各 **510** 个。

| 发现 | 细节 |
|:---|:---|
| 唯一缺失的键 | `void.tooltip`，三份中文文件均无 |
| 其英文值 | 一个**空字符串** —— 它是刻意留白的空行 |
| 实际影响 | 无；两边回退结果都是空 |
| 已注册但无名称键的物品 | **`sculk_snowball`** |
| 未加命名空间前缀的键 | 511 个中有 **211** 个不带 `bsf3lite` 前缀 |

其中两项值得留意。

`sculk_snowball` 被注册为简单物品，却没有 `item.bsf3lite.sculk_snowball` 条目，因此在任何显示它的物品栏里都会显示为原始键。它的*实体*有名称（`entity.bsf3lite.sculk_snowball` = 「Sculk Snowball」）；只有物品被漏掉了。它通常由幽匿雪球发射器产出并消耗，这也是这个缺口能一直留存的原因。

那 211 个裸键属于冲突风险而非缺陷：`itemGroup.bsf_group`、`stone_snowball.tooltip`、`weapon.tip`、`core.tip`、`random_sound.tip`、`void.tooltip` 这类名称位于全局翻译命名空间中且不带模组前缀。另一个恰好定义了 `weapon.tip` 或 `core.tip` 的模组会依加载顺序静默覆盖它或被它覆盖。

::: info
弹药兼容性指示键拼写为 `lunch_yes_cannon`、`lunch_no_shotgun` 等 —— 用 “lunch” 代替 “launch”。在源码里纯属外观问题，但会让按 `launch` 的搜索落空。
:::

## 网络

在协议版本 `"1"` 下注册了九个数据包。

| 方向 | 数据包 | 用途 |
|:---|:---|:---|
| 发往客户端 | `bsf3lite:forward_cone_particles` | 锥形粒子爆发 |
| 发往客户端 | `bsf3lite:forward_rays_particles` | 射线粒子爆发 |
| 发往客户端 | `bsf3lite:implosion_snowball_cannon_particles` | 内爆特效 |
| 发往客户端 | `bsf3lite:screenshake` | 触发屏幕震动 |
| 发往客户端 | `bsf3lite:toggle_moving_sound` | 启动或停止循环音效 |
| 发往服务端 | `bsf3lite:ammo_type` | 设置武器的选定弹药 |
| 发往服务端 | `bsf3lite:sculk_snowball_launcher_switch_sound` | 循环 meme 音效 |
| 发往服务端 | `bsf3lite:switch_tweaker_status_mode` | 循环傀儡行为 |
| 发往服务端 | `bsf3lite:switch_tweaker_target_mode` | 循环傀儡目标 |

四个客户端到服务端的处理器中有三个写得很谨慎：每一个都重新读取玩家的**主手**物品、确认它确实是预期物品，然后才在固定边界内循环一个值。来自未持有调节器或发射器的客户端的伪造包不会产生任何效果。

`bsf3lite:ammo_type` 是例外，值得精确理解：

- 它携带一个物品 id **和一个原始物品栏槽位索引**，而处理器**未校验索引**就调用 `getInventory().getItem(slot)`，因此越界值会直接进入原版物品栏代码；
- 它不要求该武器是手持物品，所以能把弹药组件写到发送者自己物品栏中任意位置的任意武器上；
- 物品 id 未经校验，因此任何注册表物品都能被写进弹药组件。

最后一点听起来比实情严重。**开火并不信任该组件**：弹药检索与弹体构造都要求存在真实的 `AbstractBSFSnowballItem` 堆叠 —— 匹配的散装堆叠，或储存类型匹配的储存罐 —— 才会发射任何东西。因此把组件设成比如 TNT，得到的是一把根本无法开火的武器，而不是 TNT 发射器。真正的暴露面是那个未检查的槽位索引，以及在正常流程之外重配自己武器的能力。

::: info
这里的一切都作用于发送方玩家自己的物品栏，因此弹药包不存在跨玩家攻击面。与那些允许数据包作用于任意坐标或任意实体的模组相比，这是个很窄的问题 —— 但审计数据包处理器的服主仍应知道，四个之中有一个没有做索引边界检查。
:::

## 客户端状态说明

武器 HUD 的上一/当前/下一弹药堆叠是作为字段存放在武器**物品实例**上的，源码注释标为仅客户端。物品对象是该类型所有堆叠共享的单例，所以这是逐物品类型的显示状态而非逐堆叠状态。在客户端只有一名本地玩家，因此它能工作 —— 但如果你要扩展本模组，这不是应当照抄的写法。
