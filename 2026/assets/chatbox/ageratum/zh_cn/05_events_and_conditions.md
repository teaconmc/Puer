# 事件与条件

渲染事件是对话除了打印文字之外做其他事情的方式。它可以附加在对话行上、任意主题组件上，或选项的 `click` 上。

## 事件形态

```json
{
  "trigger": "on_start",
  "condition": "",
  "type": "PLAY_SOUND",
  "value": "minecraft:block.note_block.bell"
}
```

| 字段 | 默认值 | 含义 |
|:---|:---|:---|
| `trigger` | `on_start` | 事件何时触发 |
| `condition` | `""` | 是否允许触发；留空表示无条件 |
| `type` | `""` | 执行哪个事件 |
| `value` | `""` | 该事件的参数 |

## 触发时机

| 触发 | 触发时刻 |
|:---|:---|
| `ON_START` | 该行或组件开始时 |
| `ON_END` | 结束时 |
| `ON_CLICK` | 组件被点击时 |
| `TICK` | 活动期间每刻 |
| `CHECK` | 状态复查时 |
| `ON_MOUSE_OVER` | 光标进入组件时 |
| `ON_MOUSE_OUT` | 光标离开时 |
| `NONE` | 自身永不触发 |

触发解析刻意做得宽松：字符串会被转为大写并按子串匹配，因此 `on_start`、`START` 与 `onStart` 都能落到 `ON_START`，鼠标触发则按同时包含 `MOUSE` 与 `OVER` 或 `OUT` 来挑选。无法识别的触发会记录一条列出全部合法值的警告并变成 `NONE` —— 事件仍被保留但永不触发，这正是游戏内「事件悄无声息地失效」的样子。

## 事件类型

| 类型 | 执行侧 | 效果 |
|:---|:---|:---|
| `COMMAND` | 服务端 | 执行一条或多条以 `;` 分隔的命令 |
| `MVEL` | 客户端，或带 `server:` 前缀时服务端 | 求值一个表达式 |
| `JUMP` | 客户端 | 跳到行下标、组，或下一行 |
| `GOTO_NEXT` | 客户端 | 允许时前进一行 |
| `PLAY_VOICE` | 客户端 | 为当前行播放语音片段 |
| `PLAY_SOUND` | 客户端 | 播放音效 |
| `STOP_SOUND` | 客户端 | 停止音效 |
| `SHOW` | 客户端 | 取消隐藏组件 |
| `HIDE` | 客户端 | 隐藏组件 |
| `REPLACE` | 客户端 | 隐藏当前组件，再显示指定组件 |
| `LOCK` | 客户端 | 锁定组件 |
| `UNLOCK` | 客户端 | 解锁组件 |
| `SET_NORMAL` | 客户端 | 把组件重置为普通状态 |
| `SET_AUTOPLAY` | 客户端 | 开启或关闭自动播放 |
| `SCALE` | 客户端 | 设置当前组件的缩放 |
| `RESTART_ANIMATION` | 客户端 | 重启立绘动画 |
| `PLAY_ANIMATION` | 客户端 | 把立绘切换到另一段动画 |

类型匹配忽略大小写。未知类型会记录一条列出全部已注册类型的警告，然后什么都不做，因此拼写错误会体现在日志里，而不会让对话崩溃。

`REPLACE` 与 `SHOW` 的区别只在它附加于组件时：它会先隐藏该组件。附加在行上时并无所属组件，其行为与 `SHOW` 完全一致。

## 条件

条件决定一个已触发的事件是否真正执行。共有三种形态，按前缀区分：

| 条件形态 | 求值位置 |
|:---|:---|
| 空字符串 | 不求值 —— 事件总是执行 |
| 以 `execute` 开头 | 服务端：作为命令执行；成功即视为「真」 |
| 以 `server:` 开头 | 服务端：作为 MVEL 求值；结果为 `true` 即视为「真」 |
| 其他任意内容 | 客户端：作为 MVEL 求值；结果为 `true` 即视为「真」 |

客户端条件廉价且即时。两种服务端形态则不然：客户端把条件字符串发给服务端，服务端求值，然后再回送一条消息来触发事件。这一来一回意味着服务端求值的条件会**晚一刻甚至更多**才落定，因此当视觉结果必须与当前帧同步时不要使用它。

::: warning
`execute` 形态会以游戏管理员权限把条件字符串当命令执行，`server:` 形态会在服务端把它编译并作为 MVEL 求值。两者都是为掌控数据包的地图作者设计的。在公开服务器上为何需要留意，见[网络与服务器注意事项](10_networking_and_server_notes)。
:::

## 选项解锁

选项的 `unlockCommand` 就是上述三种形态之一的条件。配合 `isLock`，即得到常见模式：把选项标为 `isLock: true`，再给它一个在玩家达标后变为真的 `unlockCommand`。随包演示的锁定选项用的正是物品栏检查，并用 `tooltip` 说明所需条件。

`LOCK` 与 `UNLOCK` 事件也能在运行时翻转选项状态，而 `clientSetChatOption` 允许服务端按下标改写选项的标签、悬停文本、锁定与隐藏。

## 自定义事件类型

事件类型存放在一个以大写名称为键的注册表中，因此附属模组可以注册自己的类型。一次注册需要提供客户端动作、服务端是否也需要动作，以及服务端动作。仅客户端的注册是常见情形。

这一约定中最重要的一半是：当事件声明它需要服务端时，客户端会执行自己那一半，**并且**发送数据包让服务端执行服务端那一半。一次激活会触发两半。
