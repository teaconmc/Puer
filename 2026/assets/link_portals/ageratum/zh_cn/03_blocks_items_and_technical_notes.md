# 方块、物品与技术说明

完整注册表、各部件的获取途径、传送门数据存放位置，以及值得知道的毛边。

## 完整注册表

| 类别 | ID | 说明 |
|:---|:---|:---|
| 方块 | `link_portals:portal_frame` | 环体材料；哭泣的黑曜石可作替代 |
| 方块 | 传送门方块 | 环内那层发光面；不可作为物品获得 |
| 物品 | `link_portals:portal_activator` | 右键环体点亮它；**创造分页里唯一的物品** |
| 物品 | `link_portals:portal_frame` | 方块物品 —— **不属于任何创造分页** |
| 方块实体 | 一个，用于传送门 | 承载传送门的身份信息 |
| 创造分页 | `link_portals` | 只包含激活器 |

源码共 20 个 Java 文件。**没有实体、没有命令、也没有按键绑定。**

## 获取途径才是实际限制

::: danger
**本检出根本没有 `data/` 目录** —— 因此任何东西都没有配方、没有战利品表、没有进度。

再加上创造分页只放了激活器，结果是：

| 想要 | 途径 |
|:---|:---|
| 联界门激活器 | 创造分页，或 `/give` |
| 联界门框架方块 | **只能 `/give`** —— 它不在任何分页里，创造模式搜索也看不到 |
| 生存中可用的环 | **原版哭泣的黑曜石**，模组在任何接受自有框架方块的位置都同样接受它 |

哭泣的黑曜石那条路是唯一不需要创造模式或命令的途径。见[获取开始](01_getting_started)。
:::

## 传送门数据存放在哪里

传送门存放在**世界存档数据**中，ID 为 `link_portals:portal_network`，通过 Codec 序列化。保存了两张映射表：

| 映射 | 用途 |
|:---|:---|
| 传送门 ID → 传送门信息 | 每个传送门的记录 |
| 方块坐标 → 传送门 ID | 反向查找，使传送门方块知道自己属于哪个传送门 |

每个传送门的记录包含它的 **ID、维度、出生位置、频道名称、传送门名称与朝向**。两张表在磁盘上都以字符串为键（ID 与坐标为序列化而被转成字符串），加载时重建。

两点后果：

- **传送门数据是逐世界的，不是逐玩家的。** 频道是共享的世界状态；任何人都能使用不是自己建的传送门。
- **出生位置与朝向在激活时被捕获。** 它们是记录里的字段，不会在抵达时重新计算——这正是抵达位置不对时应重新激活的原因。见[在传送门之间移动](02_travelling_between_portals)。

## 网络通信

四个数据包承载全部交互，都与那两个界面相关：

| 数据包 | 方向与作用 |
|:---|:---|
| 打开命名界面 | 服务端通知客户端打开命名界面 |
| 确认传送门名称 | 客户端把所选频道名与传送门名送回 |
| 打开传送门界面 | 服务端通知客户端打开目的地列表 |
| 选择目的地 | 客户端把选定的目的地送回 |

这个模式是正确的——**由服务端驱动界面打开并接收选择结果**，而不是客户端自行决定。

## ⚠️ 配置文件是 MDK 模板样板

模组随包一个配置类，但它是**未经修改的 NeoForge MDK 示例**。它自己的源码注释仍写着 *"An example config class… Demonstrates how to use Neo's config APIs."*。四个选项是：

| 选项 | 默认值 | 对本模组的作用 |
|:---|:---|:---|
| `logDirtBlock` | `true` | **与传送门无关** |
| `magicNumber` | `42` | **与传送门无关** |
| `magicNumberIntroduction` | `"The magic number is... "` | **与传送门无关** |
| `items` | `["minecraft:iron_ingot"]` | **与传送门无关** |

::: warning
**打开本模组的配置界面看到的是「Log Dirt Block」与「Magic Number」，而不是传送门设置。** 四个选项没有一个影响传送门；反过来，**没有任何传送门行为是可配置的**——框架尺寸、接受的材料、移动规则与频道处理全部固定在代码里。

如果你想在服务器上限制传送门建造或修改框架要求，目前没有办法。在据此做规划之前值得先知道这一点。
:::

## 本地化缺口

两份语言文件都存在，但**并不对等**，而且差异是双向的：

| 发现 | 后果 |
|:---|:---|
| `en_us` 有 **14** 键，`zh_cn` 有 **16** 键 | 不是简单的翻译滞后 |
| **`en_us` 缺少 `item.link_portals.portal_frame`** | 在英文客户端上，**框架方块的物品形式显示原始键**——方块名有翻译，物品名没有 |
| `zh_cn` 有 `item.link_portals.ice_ether` | 一个**为未注册内容准备的孤儿键**；注册表里没有这个物品，而且它的值本身还是未翻译的英文 |
| 四个配置标签在**两份文件里都是英文** | 与配置为 MDK 样板这一事实相符 |

其中英文缺失的那个物品键是唯一在游玩中可见的一处。

## 毛边汇总

| 毛边 | 影响 |
|:---|:---|
| 完全没有 `data/` | 无配方、战利品与进度；生存路线是哭泣的黑曜石 |
| 框架物品不在任何创造分页 | 只能 `/give` |
| 配置是 MDK 样板 | 任何传送门设置都不可配置 |
| `en_us` 缺框架物品键 | 英文客户端显示原始键 |
| `zh_cn` 有孤儿键 `ice_ether` | 无害的残留 |
| 出生位置/朝向在激活时固定 | 移动过环体后需重新激活 |
| 频道名留空 → `default` | 未命名的传送门全共享一个频道 |
| 骑乘中的实体不传送 | 骑马/乘船穿过无效，需先下来 |

以上没有一条会让模组无法工作——传送门系统本身是完整的，且做到了模组名所承诺的事。它们只是玩家或服主本来会在遇到时才吃惊地发现的那些点。
