# B 站对接

这是模组得名的那一层，而它是一套认真的 API 实现，而不是拼接 URL。

## 你可以给它什么

| 输入 | 解析为 |
|:---|:---|
| `BV…` 号 | 该视频的音频（在支持的设备上也含视频） |
| `av…` 号 | 同上 |
| 完整 B 站视频 URL | 同上 |
| `live:<直播间 ID>` | 某个**直播间**的音频 |
| 原始流地址 | **被拒绝** —— 见下文 |

录播与直播走**两套独立解析器**，因此行为不同：直播没有可跳转的时长，也没有固定终点。

## 直链流地址是刻意被拒绝的

模组会识别 B 站原始媒体 URL 并把它们视为**被禁止的直链**。粘贴这类地址不会生效。

这不是疏漏——**正是它保证了请求签名、CDN 选择与服务端白名单都留在链路上**。一条直链会同时绕过这三者。

## 请求带签名

B 站 Web API 要求 **WBI 签名** —— 一种用于阻挡朴素爬取的请求签名机制。模组实现了它，这正是在普通 HTTP 抓取会被拒的地方它仍能解析的原因。

请求还携带一套受管理的请求头。有两个配置字段影响它：

| 字段 | 默认 | 效果 |
|:---|:---|:---|
| `userAgent` | 空，或取自系统属性 | 覆盖发送给 B 站的 User-Agent |
| `rotateUserAgent` | 关 | 在请求之间轮换 User-Agent |

两者的存在都是为了让请求被上游 API 接受。**除非解析失败，否则不要动它们。**

## CDN 选择

一个专门的 CDN 选择器决定从 B 站哪一台分发主机取流，其状态与其余配置一起持久化。如果同一视频你卡而别人不卡，**这一层是首先该怀疑的**。

## 扫码登录

登录走的是 B 站标准 Web 流程：

1. 模组向 `passport.bilibili.com` 请求登录二维码。
2. 你用 B 站手机 App 扫描它。
3. 模组轮询登录端点直到确认扫码成功。
4. 成功后读取 `Set-Cookie` 头，保留 **`SESSDATA`** 作为登录态，拼装完整 Web Cookie，并**把两者保存进配置文件**。

登录是可选的。它的实际效果是：你账号能触及的内容与画质档位变为可用——**Dolby 音频通常就是账号门槛限定的**。

**保存下来的 Cookie 是明文的。** 这一点值得的不只是一个脚注，见 [08 技术说明与限制](08_technical_and_limits)。

登录态会在启动时恢复：若配置中存在 `sessdata`，它会被加载，并有一条日志确认会话已恢复。

## 字幕成为歌词

一个字幕服务会拉取视频的 B 站字幕并喂给**歌词投影仪**。所以这里的「歌词」不是音乐元数据查询——**就是该视频自己的字幕，按上传者的时间轴走**。

由此产生的实际后果值得知道：

- 没有字幕的视频就没有歌词可显示。
- 自动生成的字幕读起来就是自动生成的样子。
- 若某视频的字幕是译文，投影出来的就是那份译文。

## 曲目信息会被净化

解析得到的标题与元数据在写到唱片上之前会经过一个净化器。**这正是阻止任意远程文本被原样注入物品名与提示文本的机制**——当文本来自公开投稿时，这一小步卫生措施很重要。

## 播放诊断

模组专门有一个诊断组件用于播放问题，音频路径中还包含 MP3 帧同步与一条抖动（dithering）流。**如果你在追一处卡顿，模组是有仪表的，而不是沉默的。**

## 这一层不做什么

- **它不开任何端口。** 全部流量都是出站到 B 站；没有任何监听。
- **它不执行外部程序。** 解码通过随包库在进程内完成。
- **它不为其他玩家代理。** 每个客户端各自解析与解码；服务端承载控制与状态，而不是媒体。

最后这一点正是白名单有意义的原因——**服务端可以在任何客户端被要求去取流之前就拒绝该音源。**
