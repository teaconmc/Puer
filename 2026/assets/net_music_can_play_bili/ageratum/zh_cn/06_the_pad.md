# 平板

平板是本附属最大的单项功能，也是最不容易从模组名字里猜到的一个。它是一块承载**文档**的平板。

## 一份文档包含什么

| 字段 | 详情 |
|:---|:---|
| **标题** | 自由文本 |
| **作者** | 自由文本 |
| **已锁定** | 该文档是否还接受编辑 |
| **更新时间** | 一个时间戳 |
| **序列号** | 修订计数器 |
| **地图设置** | 平板地图的行为 |
| **媒体条目** | 最多 **64** 条 |
| **触发点** | 最多 **128** 个 |

两个上限都是构造文档时强制执行的硬限制——文档会被**截断**到 64 条媒体与 128 个触发点，而不是无限增长。

## 媒体条目就是唱片

你通过**添加唱片**来向平板加入媒体。每个条目会获得一个小整数 ID，从 1–64 范围内最低的空位分配，因此在增删过程中 ID 保持稳定紧凑。

这一设计有一个实际后果：**移除某条目会释放它的 ID 以供复用。** 如果你在外部笔记里写了「媒体 7」，一次编辑之后它可能指向别的东西了。

因此平板等于一座便携音乐库——**单件物品中最多 64 首曲目或视频**，可通过它自己的播放控制播放。

## 触发点

一份文档最多可附加 128 个触发点，并由一个触发**模式**选择它们的行为方式。配合地图设置，这把平板从「播放列表」变成了更接近「可编程导览」的东西：世界中的位置与媒体相关联，按模式触发。

## 锁定与发布

两项相关机制：

**锁定。** 文档可被标记为已锁定，而该记录同时暴露「设为锁定」与「复制并设为锁定」两个操作——因此锁定是**一等的状态变更**，而不是靠谁记得去检查的一个标志位。

**发布。** 存在一个专门的发布数据包，配合服务端的文档存储与存档数据。因此平板文档不是纯客户端的物品笔记：**它可以被推送到服务端、被存储、并向作者之外的人开放。**

这个组合才是重点。**一份已锁定且已发布的文档，是其他玩家可以放心查阅的稳定成品**——一份指南、一份歌单、一条导览——而不是会在他们眼前变化的草稿。

## 地图，以及它的范围

平板携带地图设置，而服务端保存**地图范围**存档数据，配有自己的世界范围数据包与一项范围同步服务。另有一个服务端采样器自检。

**「世界范围」的存在**正是平板地图区别于个人地图之处：一份文档的地图可以按世界而非仅按持有者来定义，**这才使一份已发布文档的地图对不在现场的读者也有意义**。

地图数据在客户端有磁盘缓存，并配有自己的缓存路径处理与一项路径自检。

## 服务端状态

平板有真实的服务端存在，而不只是物品数据：

| 组件 | 用途 |
|:---|:---|
| 文档存储与存档数据 | 持久化文档 |
| 持有者追踪 | 哪个玩家正持有哪块平板 |
| 状态包与状态镜像 | 让客户端保持同步 |
| 地图范围存档与同步 | 世界范围的地图定义 |

由于该状态由服务端持有，它比物品本身存活得更久——**因此需要偶尔维护**，这正是存在 **`pad refresh`** 命令的原因。该命令受权限门控，见 [07 审核与权限](07_moderation_and_permissions)。

另有一个**客户端**命令用于刷新本地地图缓存，这与刷新服务端平板状态是**不同的操作**，服务端命令自己的输出也明确这么说。

## 从平板播放同样受审核

平板播放走自己的控制数据包，而该数据包是**六个白名单执行点之一**。在启用白名单的服务器上，从平板播放某音源与从唱片机播放受完全相同的检查，且拒绝消息会明确指明「Pad播放」。

## 一处设计说明

仓库中含有一份 **15 KB 的平板设计文档**与一份 **24 KB 的小地图架构文档**，另有一个用于预览平板缓存的 Python 工具。如果你在纳闷一个 B 站音频附属为何包含一套地图子系统，答案是：**平板本身就是被当作一件独立设备来设计的，而地图是它的应用之一。**

那些文档是**规划与设计笔记**，本页只描述随包代码实际实现的内容。
